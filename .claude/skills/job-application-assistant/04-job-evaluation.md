# 04 - 岗位评估框架（通用参数化四维评分模型）

> 这是 AI 求职 Agent（通用版）的**核心差异点**。所有 `/evaluate`、`/tailor`、`/rank` 命令都调用本框架。
> 设计原则：确定性硬过滤保证可复现，LLM 推理评分保证匹配质量，打分理由保证可解释。
> **本框架不写死任何候选人、任何权重**——权重与阈值由前端「我的画像 → 评分配置」传入，硬偏好 / 红线由画像的 `careerGoal` 提供。

---

## 0. 输入

- 一个岗位 JD（文本），或一批 JD（批量模式）。
- 候选人信息（来自「我的画像」，由前端注入）：
  - `resume`：候选人简历正文。
  - `knowledge`：补充资料 / 知识库（真实经历证据，仅供引用，禁止编造）。
  - `careerGoal`：职业目标、硬偏好、风险红线、职业叙事。
  - `scoring`：`{ weights:{skill,experience,industry,growth}, threshold }`。

---

## 1. 第一步：硬性过滤（Hard Filter）

**先跑规则，再跑 LLM。** 实现方式：候选人在画像中配置的「风险红线」（`careerGoal.redLines`）是**硬性否决项**——JD 命中任一红线即 `recommend=false` 且风险块标 `red`，由系统 prompt 强制约束（`server.js` 的评估提示词「硬约束 · 风险红线」）。

常见红线示例（在画像中增删）：

| 规则 | 判定 |
| --- | --- |
| 地点不符 | JD 要求强制异地，且未标注远程友好 → 红线（不投） |
| 学历 / 资质硬门槛 | 明确要求 PhD / 强科研背景，且岗位以科研而非产品为主 → 红线（不投） |
| 纯算法 / 科研岗 | 岗位核心是模型训练 / 调参 / 发论文，非 AI 应用产品 → 红线（不投） |
| 合法性异常 | 薪资异常高、描述模糊、要求付费 / 押金、公司信息缺失 → `LEGITIMACY_RISK`（不投） |
| 无产品决策空间 | 纯执行岗（画原型 / 传话筒），无设计到落地闭环 → `LOW_GROWTH`（成长维度低分 + 风险块） |

> 注：红线判定由 LLM 依据画像红线文本执行并输出到风险块；模型输出后，`recommend` 由服务端按阈值代码重算兜底。

---

## 2. 第二步：四维 LLM 推理评分（权重由 `scoring.weights` 决定）

对 JD 逐维度给 **1.0–5.0** 分，并输出**打分理由**（可解释性要求）。

| 维度 | 默认权重（归一化前） | 评估内容 |
| --- | --- | --- |
| **技能 / 能力匹配** | 35%（可配） | JD 要求的技能与候选人核心能力重合度。"可学习"项（如某工具未用过）扣分但不硬拒 |
| **经历相关性** | 30%（可配） | 候选人过往经历与岗位职责的对口程度（引用 `resume` + `knowledge` 真实证据） |
| **行业 / 赛道匹配** | 15%（可配） | 候选人所在 / 熟悉行业与岗位行业的契合（参考 `careerGoal.industries`） |
| **职业成长价值** | 10%（可配） | 是否助力候选人职业目标、是否有决策权、团队 / 公司阶段（参考 `careerGoal`） |

**（独立）风险 / 阻断块**：地点、融资阶段、JD 硬门槛、公司合法性。**不影响 0–5 总分**，作为 flag 独立展示；命中红线时硬性否决 `recommend`。

> 维度权重与阈值完全由 `scoring` 决定；后端会对权重自动归一化（总和 = 1），按归一化权重加权。

### 打分尺度锚定（已注入服务端评分 prompt）

- **5.0**：高度匹配，几乎每条要求都能在候选人真实经历中找到对应证据。
- **4.0**：强匹配，核心要求覆盖，少量"可学习"项。
- **3.0**：部分匹配，关键要求有缺口但可弥补。
- **2.0**：弱匹配，多处硬缺口。
- **1.0**：基本不匹配。

---

## 3. 第三步：加权汇总 & 推荐阈值

```text
总分 = 技能×w1 + 经历×w2 + 行业×w3 + 成长×w4   （w 为归一化后的权重）
```

**总分与 `recommend` 由服务端代码确定性重算**（`server.js` 的 `normalizeEvalResult`），覆盖模型输出——纯计算不做成 LLM 调用。响应同时回传实际使用的 `threshold`，前端渲染以此为准。

**推荐规则（阈值由 `scoring.threshold` 决定，默认 4.0）：**

- **≥ threshold**：强烈建议投递
- **3.0 – threshold**：可投，但需在求职信 / 面试中针对性弥补缺口
- **< 3.0**：不建议投递（除非候选人在 `careerGoal` 中显式 override）

---

## 4. 第四步：风险块独立输出

无论总分高低，必须输出风险 flag：

- `LOCATION_RISK`：地点需注意
- `LEGITIMACY_RISK`：合法性存疑
- `HARD_REQUIREMENT`：存在硬性门槛（如语言 / 资质）
- `LOW_GROWTH`：职业成长价值低

> 风险块**永不拉低匹配分**，但必须可见，供候选人人工决策。

---

## 5. 输出格式（结构化，供 CSV / 仪表盘消费）

```json
{
  "job_title": "岗位名",
  "company": "公司名或未知",
  "overall_score": 4.0,
  "recommend": true,
  "dimensions": [
    {"key":"skill","name":"技能匹配","weight":0.35,"score":4.5,"rationale":"..."},
    {"key":"experience","name":"经历相关性","weight":0.30,"score":4.6,"rationale":"..."},
    {"key":"industry","name":"行业匹配","weight":0.15,"score":4.0,"rationale":"..."},
    {"key":"growth","name":"职业成长","weight":0.10,"score":4.5,"rationale":"..."}
  ],
  "risks": [{"level":"green|yellow|red","title":"...","detail":"..."}],
  "summary": "一句话结论"
}
```

---

## 6. 诚实约束（Honesty Rule，绝不违反）

- **禁止虚构任何经历、技能、数据。** 简历定制只能基于 `resume` + `knowledge` 的真实内容重组表达。
- 若 JD 要求某能力候选人不具备，必须标为"风险点 / 缺口"，**不得编造对应经历**。
- 所有打分理由必须能回溯到候选人的真实资料，不可凭空断言。
